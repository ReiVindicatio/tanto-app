# チケット

> 作りたいもの・直したいものを1件1ファイルで貯め、状態を管理する。**一覧（下のボード）は、チケットの状態を変えたら必ず更新する。**
> できていること・できていないことの全体は 📖 [docs/features.md](../docs/features.md)

## 進め方

```
起票 → 議論中 → 議論済み → 設計中 → 設計レビュー → 実装中 → 実装レビュー → 完了
                                   （どこからでも）→ 保留／却下
```

| 状態 | やること | 誰が |
|---|---|---|
| **起票** | 目的と背景だけ書く。思いついたらとりあえず置く | 誰でも |
| **議論中** | 何をやるか・やらないか、選択肢と勧めを書き、決める | Claude が案を出し、ユーザーが決める |
| **議論済み** | 方針は決まったが、まだ設計に入っていない（依存するチケットの完了待ちなど） | |
| **設計中** | チケットに設計を書く（データ・画面・影響範囲・テスト方法・完了条件） | Claude |
| **設計レビュー** | 設計を読んで OK／修正を出す | ユーザー |
| **実装中** | 設計どおりに作る。設計から外れるときは止めて相談する | Claude |
| **実装レビュー** | 差分と動作を確認する（Claude はセルフレビューとテストの結果を添える） | ユーザー |
| **完了** | features.md を更新し、チケットに結果を書く | Claude |

- **設計レビューを省いてよいもの**：見た目の小さな修正、文言、バグ修正（データ・スキーマ・方針に触れないもの）。省いたときはチケットに「設計レビュー省略」と書く
- **省いてはいけないもの**：スキーマ・データモデル・方針（CLAUDE.md の「変更内容を提示して合意を得てから」）、ユーザーの学習記録に触れるもの、外部サービスを使うもの
- 1回のセッションで扱うのは、原則として**1チケット**。状態が変わったらボードを更新して commit する
- 決めたことの経緯で残す価値があるものは、従来どおり `docs/decisions/` にも書く
- **実装レビューのやり方**（2026-10-18 決定）：当面は、Claude が差分の要点・テストや動作確認の結果をまとめて見せ、ユーザーが判断する。CI（T001）が入ったら、チケットごとのブランチと GitHub の PR に移るかを改めて決める

## チケットの書き方

ファイル名：`T<3桁>-<短い英語>.md`。番号は増やすだけ（欠番・再利用しない）。

```markdown
# T000 タイトル

- 状態：起票
- マイルストーン：M1 基盤
- 優先度：高／中／低
- 依存：T000
- 更新：YYYY-MM-DD

## 目的・背景
## 議論（選択肢と勧め、決まったこと）
## 設計
## 完了条件
## 結果（完了時）
```
