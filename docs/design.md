## 0. 結論（先に）

1. **最初のスコープは「予備・刑法・R08-2026」にする。**R08 は全科目テキスト層があり、OCR なしで一気通貫を通せる。しかも刑法の13問に、組合せ・2つ選ぶ・会話（見解）・個数・穴埋めの各形式が入っていて、**データモデルの試験台として都合がいい**
2. **テキスト層が正常な PDF には AI 補正をかけない。**`pdftotext` の出力は PDF 内の文字データそのものなので、AI を通すと「直しすぎ」の危険だけが増える。AI 補正は OCR 由来と、決定的パースが失敗した箇所に限る
3. **肢の○×は、形式ごとに「導出できる／できない」をルールで決める。**導出できない形式（個数問題・部分点つき・穴埋め）を無理に肢に割ると、正しい記述を×として覚えさせる事故になる。導出できないものは問題カードにする
4. **復習（FSRS）の単位は肢を基本にする。**ただし同じ問題の肢は同じ日に1枚まで（兄弟の抑制）
5. **「現行法での正誤」は AI に判定させない。**改正情報（施行日・対象条文）から「影響しうる肢」にフラグを立て、人が確認する
6. 🔴 **一番のリスクは AI 解説の誤り。**報告タブは事後の手段なので、公開前のゲート（公式正解との矛盾チェック・条文は e-Gov の本文だけ・判例は確認できたものだけ）を先に作る

## 2. 抽出パイプライン

### 各段階の入出力

| # | 段階 | 入力 | 出力 | 方式 | ここで止める条件 |
|---|---|---|---|---|---|
| 0 | 取得 | `sources/manifest.json`（URL） | `data/raw/*.pdf`＋sha256（既存244件はコピー済み。抜けと新年度だけ取得） | 決定的 | 取り直した PDF の sha256 が manifest と違う（法務省側の差し替え） |
| 1 | テキスト化 | PDF | `data/extracted/…/*.txt`＋`.meta.json`（方式・ページ境界・品質スコア） | `pdftotext -layout`。品質スコアが閾値未満なら OCR | 品質スコアが OCR 後も閾値未満 |
| 2a | 問題の構造化 | テキスト | `data/parsed/…/<科目>.json`（問・No・配点・リード文・前提文・肢） | **決定的**（正規表現＋形式判定） | 問番号・No が連番でない |
| 2b | 正答の構造化 | 正答 PDF のテキスト | No→解答・配点・備考（順不同・部分点） | **決定的** | 下の検証に1つでも落ちる |
| 3 | 検証 | 2a＋2b | `reports/validation/…md` | 決定的 | 1つでも ❌ |
| 4 | AI 補正 | 段階1の該当箇所（＋ページ画像） | `data/corrections/…jsonl`（原文・補正後・差分） | **AI**（OCR 由来と、2a で失敗した箇所だけ） | 差分が許容範囲を超える（下記） |
| 5 | 肢の○×導出 | 2a＋2b＋形式 | 肢ごとの `truth_at_exam` と導出方法 | **決定的** | 導出ルールにない形式 |
| 6 | 解説生成 | 肢＋問の前提文＋公式の○×＋条文本文（e-Gov） | `data/explanations/…`（版つき） | **AI** | 公式の○×と矛盾／根拠条文が取得できない |
| 7 | 書き出し | 正本データ | `app/public/data/…json`（科目・年度ごとの束） | 決定的 | — |

### 段階3の検証（問題番号と正答のずれを防ぐ）

- **問数・No 数**：科目ごとの問番号が 1..N の連番か。No が 1..M の連番か。予備の各科目は配点の合計が30点になるか（`（配点：２）` の和と、正答表の配点の和の両方。R08 刑法で13問・30点を確認済み）
- **対応**：問題文の `［No.◯］` の集合と、正答表の No の集合が一致するか
- **値域**：組合せ・択一の解答が 1〜5 の範囲か。順不同の No は2つ以上あるか
- **形式との整合**：「誤っているものの組合せ」なのに、導出した×が1個や4個になっていないか（想定外の分布は止める）
- **ページ境界**：肢がページをまたいで切れていないか（`- 3 -` などのページ番号行が肢の本文に混入していないか）
- **年度をまたいだ整合**（後から）：同じ記述が別年度で逆の○×になっていないか（yobishiken で1件成功した検証）

### 段階4：AI 補正で「直しすぎ」を検知する

- **保存するもの**：原文スパン／補正後／差分（文字単位）／補正理由／モデル・プロンプトの版／採用した人と日時
- **許容する差分**：OCR で起きやすい置換（「続→統」「元本→本」「β→B」「イ→↑」の型）と、改行・空白。**語句の追加・削除・語順の変更は自動では採用しない**
- **数値で止める**：スパンごとの文字変更率が閾値（例：5%）を超えたら人の確認へ。否定語（「ない」「できない」「しない」）、数字、条文番号、「及び／又は」が変わった差分は、変更率に関係なく必ず人の確認へ（**1字で正誤が反転する**）
- **入力にページ画像を添える**：テキストだけで補正させると、もっともらしい文に書き換える方向に流れる

### 段階6：解説生成のルール

- **公式の○×は入力で固定する。**モデルに○×を判定させない。モデルが「この記述は（公式と逆に）正しい」と書いた場合は、**解説を捨てずにフラグを立てる**。パースの誤り・正答表の読み違い・法改正のどれかを示す信号になる
- **根拠条文は e-Gov 法令 API から取得した本文だけを引用する**（取得日と本文のハッシュを残す）。モデルの記憶で条文の文言を書かせない
- **判例は、事件の呼び名と年月日を出すが、検索などで確認できたものに限る。**確認できないものは「判例あり（要確認）」とだけ書く
- **AI 生成であること・版・生成日を解説に表示する**

## 3. データモデル（JSON スキーマ案）

### 3.1 全体の階層

```
Exam（試験・年度）
 └ Question（問）
     ├ answer_slots[]（No ごとの公式解答）
     ├ context（前提文：会話・見解・事例・語群）
     └ Statement[]（肢）
         └ Explanation[]（解説・版つき）
Report（誤り報告）→ Explanation の新しい版
Correction（AI 補正の記録）→ Source のスパン
```

### 3.2 Question（問）

> 📖 実装では `context` を配列にし、`exhaustive`・`unordered`・`choices` などを足した（`decisions/003`）。現行の形は `data/questions/yobi/2026/keiho.json`

```json
{
  "id": "yobi-2026-keiho-q13",
  "exam": { "type": "yobi", "year": 2026, "era": "R08" },
  "subject": "keiho",
  "number": 13,
  "points": 3,
  "format": "fill_blank",
  "polarity": null,
  "stem": "リード文（〜のうちどれか）",
  "context": { "kind": "dialogue", "text": "【学生Ａ】…" },
  "answer_slots": [
    { "no": 15, "official_answer": 2, "unordered_group": null },
    { "no": 16, "official_answer": 4, "unordered_group": null }
  ],
  "scoring": { "partial_credit": "4問正解で部分点2点", "raw_note": "備考欄の原文" },
  "status": { "voided": false, "all_correct": false, "errata": [] },
  "statements": ["yobi-2026-keiho-q13-a", "..."],
  "statement_truth_derivable": false,
  "provenance": { "source_id": "yobi-2026-tanto-keikei-q", "page": 11, "extraction": "pdftotext" },
  "flags": []
}
```

### 3.3 `format` と、肢の○×を導出できるか

> 📖 導出の根拠を `truth_at_exam.basis`（direct／selected／exhaustive／uniqueness／convention）で区別する（`decisions/003`）

| format | 例 | 肢の○×の導出 | 復習の単位 |
|---|---|---|---|
| `combination` | 誤っているものの組合せ（解答1〜5） | **できる**（選ばれた組の肢が polarity 側） | 肢 |
| `single_choice` | 誤っているものを1つ選べ | **できる** | 肢 |
| `multi_select_unordered` | 2つ選べ（順不同の No が2つ） | **できる**（No の集合が polarity 側） | 肢 |
| `true_false_each` | 各記述が正しければ1、誤りなら2（No ごと） | **できる**（No＝肢） | 肢 |
| `context_dependent` | 【見解】に立った場合に正しいもの／学生の会話 | **できるが、前提文なしでは意味が変わる** → `requires_context: true` | 肢（前提文つきで出す） |
| `count` | 正しいものは幾つあるか | **できない**（個数だけでは、どの肢かが決まらない） | 問 |
| `fill_blank` | 空欄に入る語の組合せ | **肢がない**（空欄ごとの選択） | 問（空欄ごとの小問にはできる） |
| `ordering` | 並べ替え | 肢がない | 問 |

- `polarity`：`"incorrect"`（誤っているもの）／`"correct"`（正しいもの）／`null`。**リード文から決まらないものは `null` にし、導出しない**
- **部分点つきの問**は、公式解答そのものは No ごとに確定しているので導出に影響しない。採点の表示だけに使う

### 3.4 Statement（肢）

```json
{
  "id": "yobi-2026-keiho-q01-a",
  "question_id": "yobi-2026-keiho-q01",
  "label": "ア",
  "text": "真正不作為犯と不真正不作為犯との違いは、…",
  "requires_context": false,
  "truth_at_exam": {
    "value": true,
    "derivation": "combination",
    "derived_from": { "slot_no": 1, "official_answer": 5 }
  },
  "truth_current": {
    "status": "unreviewed",
    "value": null,
    "basis": null,
    "law_change_refs": [],
    "reviewed_by": null,
    "reviewed_at": null
  },
  "tags": { "articles": ["刑法43条"], "topics": ["不作為犯"] }
}
```

- **`truth_at_exam`（出題時点の正解）は公式データからの導出だけで決まる。**人も AI も書き換えない（訂正は法務省の正誤訂正・没問の公表を取り込むときだけ）
- **`truth_current`（現行法での正誤）は別枠。**`status` は `unreviewed`／`unchanged`／`changed`／`uncertain`。既定は `unreviewed`
  - 改正情報（`data/law-changes/`：施行日・対象条文）と、出題年度・肢の条文タグを突き合わせ、**影響しうる肢にだけ `law_change_refs` を付けて確認待ちにする**
  - アプリでは、`changed` の肢は「出題時点では○／現行法では×」と両方を見せる。`unreviewed` で改正の影響がありうる肢には注意書きを出す
  - 刑法では、拘禁刑の創設（懲役・禁錮の一本化）や性犯罪規定の改正（不同意性交等罪など）が典型（⚠️ 施行日・対象条文は実装時に e-Gov で確認する）
- **没問・全員正解扱い**は Question の `status`（`voided`・`all_correct`・`errata`）に置き、そこに属する肢は出題対象から外すか注記する。**複数正解**は `answer_slots[].official_answer` を配列にできるようにしておく

### 3.5 Explanation（解説）と版管理

> 📖 実装では問ごとに1ファイル（`data/explanations/<exam>/<year>/<subject>/qNN.json`）にした（`decisions/004`）。指示は `prompts/explain-v1.md`、検査は `pipeline/check_explanations.py`

```json
{
  "id": "exp-yobi-2026-keiho-q01-a",
  "target": { "type": "statement", "id": "yobi-2026-keiho-q01-a" },
  "version": 3,
  "status": "published",
  "body": "…",
  "citations": [
    { "type": "statute", "law": "刑法", "article": "43", "source": "e-Gov API", "fetched_at": "2026-10-20", "text_sha256": "…" },
    { "type": "case", "name": "（事件の呼び名）", "court": "最高裁", "date": "…", "verification": "searched" }
  ],
  "consistency": { "matches_official_truth": true, "checked_at": "…" },
  "generated_by": { "model": "…", "prompt_version": "explain-v1", "generated_at": "…" },
  "history": [
    { "version": 2, "status": "superseded", "reason": "report-0012：条文番号の誤り", "changed_at": "…" }
  ]
}
```

- `citations[].verification`：`searched`（検索で確認）／`human`（人が判例集・六法で照合）／`unverified`（出さない）
- **版は追記だけ**（上書きしない）。報告で直したら `history` に前の版と理由を残す

### 3.6 Report（誤り報告）

```json
{ "id": "report-0012", "target": { "type": "statement|question|explanation", "id": "…" },
  "kind": "text_typo|truth_wrong|explanation_wrong|law_changed|other",
  "message": "…", "created_at": "…", "status": "open|accepted|rejected",
  "resolution": { "explanation_version": 3, "note": "…" } }
```

- **`truth_wrong`（公式の○×が違う）という報告**は、パースの誤りか正誤訂正の取り込み漏れを示す。**解説の修正ではなく、段階2〜5のやり直しにつなぐ**

### 3.7 FSRS：肢単位か問題単位か

**肢単位を基本にすることを勧める。**

- 一問一答の学習対象は「この記述は正しいか」で、組合せ問題はその合成にすぎない。問題単位で復習すると、**5つの肢のどれが分かっていないか**の情報が消える
- **同じ問の肢は、同じ日に1枚まで**（兄弟の抑制）。同じリード文・前提文を続けて見ると、2枚目以降が前の肢の記憶で答えられてしまう
- `requires_context: true` の肢は、前提文と一緒に出す。単位は肢のまま
- **導出できない形式（`count`・`fill_blank`・`ordering`）は問題単位**のカードにする
- 本番形式の練習（問題単位・時間つき）は別モードにし、FSRS の対象にしない（間隔反復と模試の目的が違う）
- 復習の記録は肢単位で持ち、問・科目単位の集計はそこから作る

### ホスティング（📖 `decisions/001`）

- **静的サイトで足りる。**問・肢・解説は変化の少ない JSON で、全科目・全年度でも数 MB の見込み。復習の記録は端末内（IndexedDB）に置く → サーバーなし・オフライン可・Capacitor にそのまま載る
- **第一候補は Cloudflare Pages。**Vercel の Hobby（無料）は商用利用を禁じ、広告を載せると商用利用に当たると明記している。GitHub Pages もオンラインビジネス向けの利用を認めていない
- ~~Supabase は、端末をまたいだ同期と報告タブを公開するときに足す。~~ → 2026-10-19 変更：ログイン＝Firebase Authentication、API＝Cloudflare Workers、DB＝Cloudflare D1（📖 `decisions/012`）
- FSRS は既存の実装（TypeScript のライブラリ）を使い、自作しない

### yobishiken（学習用リポジトリ）との共存

- **過去問データの正本はこのリポジトリの `data/questions/`。**yobishiken の `kakomon/構造化データ/` は旧版として残し、新しく作り直さない
- yobishiken はこのリポジトリの書き出し（JSON／Anki 用 TSV）を**読む側**にする。パスで直接参照しない（リポジトリをまたいだ相対パスは壊れやすい）

## 5. トークン量の見積もり方法（刑法1年度分）

### 測り方

1. **実物で数える。**`messages.count_tokens` に、本番で送るプロンプト（指示＋問の本文＋前提文＋条文本文）をそのまま渡す。モデル ID も本番と同じものにする（トークン数はモデルごとに違う）。tiktoken などの他社のトークナイザでは数えない
2. **形式ごとに1問ずつ試す。**R08 刑法なら、組合せ（問1）・会話の穴埋め（問3）・個数（問12）・各肢○×（問13）の4問。入力は `count_tokens`、出力は実際に生成して `usage.output_tokens` を見る（思考のトークンは出力として課金される）
3. **掛け算する。**1問あたりの入力×問数、出力×問数。解説は「1問ずつまとめて生成（5肢を1回で）」か「肢ごと」かで入力が5倍変わるので、両方を試して品質と費用を比べる

### 目安（仮置き。上の測定で置き換える）

| 項目 | R08 刑法 |
|---|---|
| 問題文の量 | 刑法の部分で約12,700字・13問・No.1〜19 |
| AI 補正 | **0**（テキスト層が正常なのでかけない） |
| 解説（1問ずつ・13回） | 入力 1回あたり数千トークン（指示＋問題＋条文）、出力 1回あたり数千トークン（5肢分の解説＋思考） |

- 費用は「入力トークン×入力単価＋出力トークン×出力単価」。**Batch API を使えば半額**になり、急がない生成（科目ごとに少しずつ流す方針）と相性がいい。指示部分が共通なのでプロンプトキャッシュも効く
- 単価はモデルで大きく違う（例：Opus 5.5 は入力 $4／出力 $20 per 100万トークン、Haiku 5.5 は $0.10／$0.50）。**解説の品質が費用より重要なので、まず高いモデルで品質の基準を作り、安いモデルで同じ品質が出るかを後から比べる**
- 🔴 **決定：解説は Claude Code のセッションで生成する**（📖 `decisions/001`）。API 課金はなく、上の見積もりは「1セッションで何問進むか」の目安として使う。1問ずつ生成して書き出し、トークンが切れたら次のセッションで続きから再開する。再現性は、指示ファイルの版（`prompts/explain-vN.md`）と解説ファイル側の記録（`prompt_version`・生成日）で補う

## 6. 危ない点

1. **利用規約**：法務省サイトは「公共データ利用規約（第1.0版）」（PDL1.0）を適用していて、複製・公衆送信・翻案ができ、商用利用も可能（広告収入も可）。ただし条件がある
   - **出典の記載**（「出典：法務省ウェブサイト（URL）」）と、**編集・加工したことの記載**が必要
   - 🔴 **「あたかも国が作成したかのような態様」で公表してはいけない。**アプリ名・アイコン・画面で公式感を出さない。AI 解説は「このアプリが作成」と明示する
   - **第三者が著作権を持つ部分は対象外になりうる**（一般教養の引用文、憲法の資料文など）。**一般教養はスコープから外す**のを勧める
   - 🔍 [法務省ウェブサイトのコンテンツの利用について](https://www.moj.go.jp/hisho06_00280.html)／[PDL1.0（デジタル庁）](https://www.digital.go.jp/resources/open_data/public_data_license_v1.0)
2. 🔴 **AI 解説の誤り**：法律の学習アプリで誤った解説を出すと、利用者がそれを覚える。報告タブは事後の手段にすぎない。公開前のゲート（§2 段階6）を先に作り、**自分が学習を終えた科目から公開する**（「学習の進捗に合わせて流す」方針と一致する）
3. **肢の○×の導出の限界**：個数問題などを無理に肢に割ると、正しい記述を×として覚えさせる。yobishiken の民商民訴でも148問が導出できていない。**導出できないものは捨てずに問題カードにする**
4. **法改正**：刑法は直近で大きい改正がある。古い年度の肢は、出題時点の○×のまま出すと現行法と食い違う。**AI に現行法の正誤を判定させない**（§3.4）
5. **正誤訂正・没問**：法務省は試験後に正誤訂正や採点上の取扱いを公表することがある（yobishiken の `kakomon/予備試験/資料/` に正誤訂正の PDF がある年度がある）。**正答 PDF の備考欄と、資料の PDF を必ず取り込む**
6. **ストア審査**：Web をそのまま包んだだけのアプリは、ストアの審査で機能が少ないとして通らないことがある（⚠️ 審査基準は申請時に確認）。オフライン学習・通知など、端末側の機能を足す前提で設計する
7. **R07 の3科目群と H25・H26 の一部は OCR が要る。**最初のスコープ（R08）では出てこないので、パイプラインの OCR の段は2本目の年度で通す
