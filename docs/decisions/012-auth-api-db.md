# ログインは Firebase Authentication、記録は自前の API（Cloudflare Workers）経由で Cloudflare D1 に置く（2026-10-19）

> 決定の記録。**以後編集しない。**運用の現行版は `tickets/T003-login-sync.md`・`docs/design.md`。

## 何が起きたか

T003（ログインと端末間同期）は、決定001・T003 の議論で「Supabase（Auth＋Postgres）」としていた。設計に入る前に、ユーザーから次の要望・懸念があった。

- ログインは Google だけでよい
- Supabase の無料プランは、1週間アクセスがないとプロジェクトが一時停止する
- **いずれ公開することを念頭に置き、利用者数を見ながら DB だけを入れ替えれば済む設計にしたい**

## 決めたこと

ログイン・API・DB の3層に分け、それぞれを入れ替えられるようにする。

| 層 | 最初の選択 | 入れ替えるとき |
|---|---|---|
| ログイン | **Firebase Authentication**（Google ログイン） | API での ID トークンの検証のしかたが変わるだけ |
| API | **Cloudflare Workers**（公開先の Worker に `/api` を足す） | ほぼ変えない |
| DB | **Cloudflare D1** | API の中の保存処理を差し替えるだけ。アプリ側は変わらない |

- アプリから DB を直接触らせない（必ず API を通す）。API は ID トークンを検証して利用者を特定し、その人の記録だけを読み書きする
- サーバーに置くのは回答ログだけ（T003 の決定を引き継ぐ）。FSRS の状態は端末で回答ログから作る

## 理由

- **認証は自前で書かない**：事故が起きやすい部分を Firebase に任せる。公開時に Apple ログインなどを足すのも設定で済む
- **DB の入れ替えをアプリに波及させない**：Firebase だけで完結させる（アプリが Firestore を直接読み書きする）案だと、DB を替えるときにアプリまで直すことになる
- **止まらない・無料の範囲が大きい**：D1 は一時停止がない。無料で書き込み10万行／日・5GB（公式ドキュメント、2026-10-19 確認）
- 公開後に要る仕組み（使いすぎの制限、退会時のデータ削除）を API に置ける

## 採らなかったこと

- **Supabase**：1週間アクセスがないと一時停止する。定期的にアクセスして止まらなくする方法は、規約の趣旨に反するおそれがある
- **Firebase だけ（Auth＋Firestore を直接）**：DB の入れ替えがアプリに波及する
- **Cloudflare D1＋自前の Google ログイン**：認証の処理（OAuth の流れ・トークンの検証・セッション）を自分たちで持つことになる
