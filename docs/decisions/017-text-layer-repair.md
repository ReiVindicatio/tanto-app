# テキスト層が壊れた PDF は、OCR でなくフォントの照合で決定的に復元する（2026-10-19）

> 決定の記録。**以後編集しない。**手順の現行版は `pipeline/repair_text.py`。

## 何が起きたか

T010（OCR）に着手して調べたところ、needs_ocr の5件（予備 R07 の3科目群・H25／H26 憲法行政法）はどれも画像ではなく、文字のデータは PDF に入っていた。壊れ方は2通り。

1. **文字の対応表（ToUnicode）がない**（R07 全体、H25・H26 のページ番号と H26 の1ページ）。文字コードが MS 明朝・MS ゴシックの字形番号（GID）のままで、pdftotext が字形番号をそのまま文字として出していた
2. **見えない文字の層が重なっている**（H25・H26）。InDesign で貼り込まれた一般教養の PDF の文字が、ページ下端の帯にクリップされて見えないまま、テキストとしては残っていた。見えている憲法・行政法の文字は正常

## 決めたこと（ユーザーから T010 の進め方を任された：「おすすめで」）

- OCR は使わず、`pipeline/repair_text.py` で PDF の一時コピーを直してから pdftotext にかける。`data/raw/` の PDF は変えない
  - 1 → 手元の MS 明朝・MS ゴシック（Microsoft Office 同梱、5.30）の cmap から GID → 文字の ToUnicode を作って足す。**足す前に、埋め込まれた字形が手元のフォントの同じ番号の字形と一致することを確かめる**（TrueType は輪郭の座標が完全に一致。CFF に変換されたものは面積・重心・広がりが許容差の範囲で一致）。一致しない字形が1つでもあれば止める
  - 2 → クリップの矩形の外から始まる文字の描画を除く。除いた文字に ToUnicode のあるフォントのもの（見えている本文）が1つでもあれば止める
- 結果は禁止事項3の「AI 補正」にも「OCR 由来」にも当たらない（推測が入らず、字形と文字の対応で決まる）。人の確認は要らない。検証（段階3）と導出の矛盾検査は通常どおり通す
- この段だけ pypdf・fontTools と手元のフォントが要る。フォントは commit しない。復元した `data/extracted/` を commit するので、段階2以降（regen.py・CI）はこれらなしで動く
- extract.py は、復元済みのファイルを上書きしない

## 採らなかったこと

- **OCR（Vision・Tesseract）**：誤読が否定語・数字にも出て、補正の採用に人の確認が要る。文字のデータがあるのに使わない理由がない
- **pdftotext の出力を後から置き換える**：字形番号がアラビア文字などの範囲に当たると、pdftotext が右から左の文字として並べ替える（R07 憲法行政法の「ア○ イ○ ウ○」で起きた）。ToUnicode を足してから pdftotext にかければ起きない

## 結果

- 5件とも品質スコア 1.000。予備の法律7科目がすべて16年度（H23〜R08）そろった
